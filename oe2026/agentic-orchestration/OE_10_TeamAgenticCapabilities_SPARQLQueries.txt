# The top three competency questions are CQ 1, CQ 3 and CQ 5 of the use case. Each has one main query. CQ 1 and CQ 5 also

# answer given with it.
#
# CQ 1 follows the semantic processes of the use case in order, starting from Ken's request:
#   step 1: the skills, tools and MCP servers that satisfy the information requirements and hard constraints of the
#           request (semantic lookup);
#   step 2: the candidate orchestration plans whose steps meet every requirement and hard constraint, violate none,
#           and receive each input from an earlier step (dependency and constraint-based reasoning);
#   then the CQ 1 query and its supporting queries: how the candidates were evaluated on Ken's soft constraints and
#           which one is selected and which rejected (multi-criteria plan evaluation).
# The step 1 and step 2 queries avoid FILTER NOT EXISTS and property paths, which Snap SPARQL does not support; step 2
# uses MINUS instead. They were run with the other queries through the Snap SPARQL Query plugin 6.0.0 on
# 2026-10-30.

PREFIX rdfs:           <http://www.w3.org/2000/01/rdf-schema#>
PREFIX skos:           <http://www.w3.org/2004/02/skos/core#>
PREFIX prov:           <http://www.w3.org/ns/prov#>
PREFIX agento:         <http://www.w3id.org/agentic-ai/onto#>
PREFIX oe-agtorch:     <https://tw.rpi.edu/ontology-engineering/oe2026/agentic-orchestration/>
PREFIX oe-agtorch-ind: <https://tw.rpi.edu/ontology-engineering/oe2026/agentic-orchestration/agentic-orchestration-individuals/>
# ======================================================================================================================
# CQ 1, step 2 (dependency and constraint-based reasoning): which candidate orchestration plans can answer Ken's
#       request, and which of their steps meet his information requirements and hard constraints?
# Reasoning: OWL 2 DL entailment (needs a DL reasoner). Run in Snap SPARQL with HermiT or Pellet started. Without a
#   reasoner the query returns no rows, because every property it uses below except hasStep, hasAssociatedTask,
#   performedBySkill, expresses and violatesConstraint is inferred and never asserted.
#   The reasoner infers these triples from OWL 2 property chains ("o" composes properties; isX is the reflexive
#   marker of class X, defined by X EquivalentTo isX Self, so a chain can test that an element belongs to X):
#   - request to constraint (request -> person -> preference setting -> constraint):
#       hasPreferenceSetting        <- isRequest o prov:wasAttributedTo o inverse(prov:wasAttributedTo) o isPreferenceSetting
#       hasHardConstraint           <- hasPreferenceSetting o inverse(prov:wasDerivedFrom) o isHardConstraint
#       hasHardConstraint           <- isRequest o inverse(prov:wasDerivedFrom) o isHardConstraint
#     so kenRequest hasHardConstraint kenEvidenceConstraint (Ken -> kenSettings -> kenEvidenceConstraint).
#   - step to what it satisfies, through the capability its task requires:
#       stepRequiresCapability      <- agento:hasAssociatedTask o agento:requiresCapability
#       stepSatisfiesRequirement    <- stepRequiresCapability o satisfiesRequirement
#       stepSatisfiesHardConstraint <- stepRequiresCapability o satisfiesConstraint o isHardConstraint
#   - plan to what its steps satisfy, consume and produce:
#       planSatisfiesRequirement    <- hasStep o stepSatisfiesRequirement
#       planSatisfiesHardConstraint <- hasStep o stepSatisfiesHardConstraint
#       hasTask                     <- hasStep o agento:hasAssociatedTask
#       planConsumes                <- hasTask o consumes
#       planProduces                <- hasTask o produces
#   - class membership: CandidateOrchestrationPlan is the union of SelectedOrchestrationPlan and
#     RejectedOrchestrationPlan, so kenPlan1 (inferred selected) and kenPlan2 (inferred rejected) are candidates.
#   The query keeps a plan for Ken's request only if
#   (a) every information requirement the request expresses is in planSatisfiesRequirement of the plan,
#   (b) every hard constraint in hasHardConstraint of the request is in planSatisfiesHardConstraint of the plan, and
#       the plan violates no hard constraint,
#   (c) every information artifact in planConsumes of the plan is also in planProduces, so no step waits for an input
#       the plan never creates. (Without property paths the query cannot follow agento:nextStep to check that the
#       producing step comes earlier; CQ 2 derives the step order from these inputs and outputs.)
#   These "every" checks stay in SPARQL as nested MINUS (a requirement exists that the plan does not satisfy): under
#   OWL's open-world assumption, and in SWRL, which has no negation, a reasoner cannot conclude that something is
#   missing. For each plan that is kept, the query lists the steps whose stepSatisfiesRequirement or
#   stepSatisfiesHardConstraint links them to Ken's requirements and hard constraint, with the skill that performs
#   the step's task. Ken's soft constraints are not satisfied by a step; they are measured by the decision criteria of
#   the plan evaluations (CQ 1 supporting query). Which candidate is then selected is the CQ 1 query below.
# Individuals: kenRequest, Ken, kenSettings, his information requirements (needAffordableProducts, needEvidenceForKen,
#   needMuscleSupplements) and hard constraint kenEvidenceConstraint; kenPlan1 and kenPlan2 with their steps, tasks,
#   information artifacts and plan evaluations; the capabilities and skills of step 1.
# Expected answer: both of Ken's plans are candidates; plan 2 verifies evidence in two steps (10 rows):
#   plan | requirement | constraint | stepLabel | skill
#   kenPlan1 | needAffordableProducts |  | Ken plan 1, step 4 | productSelectionSkill
#   kenPlan1 | needEvidenceForKen |  | Ken plan 1, step 6 | evidenceVerificationSkill
#   kenPlan1 | needMuscleSupplements |  | Ken plan 1, step 2 | personalizedSupplementRecommendationSkill
#   kenPlan1 |  | kenEvidenceConstraint | Ken plan 1, step 6 | evidenceVerificationSkill
#   kenPlan2 | needAffordableProducts |  | Ken plan 2, step 2 | productSelectionSkill
#   kenPlan2 | needEvidenceForKen |  | Ken plan 2, step 3 | evidenceVerificationSkill
#   kenPlan2 | needEvidenceForKen |  | Ken plan 2, step 5 | evidenceVerificationSkill
#   kenPlan2 | needMuscleSupplements |  | Ken plan 2, step 1 | personalizedSupplementRecommendationSkill
#   kenPlan2 |  | kenEvidenceConstraint | Ken plan 2, step 3 | evidenceVerificationSkill
#   kenPlan2 |  | kenEvidenceConstraint | Ken plan 2, step 5 | evidenceVerificationSkill
SELECT ?plan ?requirement ?constraint ?stepLabel ?skill
WHERE {
  ?plan a oe-agtorch:CandidateOrchestrationPlan .
  ?plan oe-agtorch:addresses oe-agtorch-ind:kenRequest .
  # (a) drop the plan if it leaves an information requirement of the request unsatisfied
  MINUS {
    oe-agtorch-ind:kenRequest oe-agtorch:expresses ?r1 .
    ?r1 a oe-agtorch:InformationRequirement .
    MINUS { ?plan oe-agtorch:planSatisfiesRequirement ?r1 . }
  }
  # (b) drop the plan if it leaves a hard constraint of the request unsatisfied, or violates one
  MINUS {
    oe-agtorch-ind:kenRequest oe-agtorch:hasHardConstraint ?h2 .
    MINUS { ?plan oe-agtorch:planSatisfiesHardConstraint ?h2 . }
  }
  MINUS { ?plan oe-agtorch:violatesConstraint ?h3 . }
  # (c) drop the plan if it consumes an information artifact that it never produces
  MINUS {
    ?plan oe-agtorch:planConsumes ?artifact .
    MINUS { ?plan oe-agtorch:planProduces ?artifact . }
  }
  ?plan oe-agtorch:hasStep ?step .
  ?step rdfs:label ?stepLabel .
  ?step agento:hasAssociatedTask ?task .
  ?task oe-agtorch:performedBySkill ?skill .
  {
    oe-agtorch-ind:kenRequest oe-agtorch:expresses ?requirement .
    ?step oe-agtorch:stepSatisfiesRequirement ?requirement .
  }
  UNION
  {
    oe-agtorch-ind:kenRequest oe-agtorch:hasHardConstraint ?constraint .
    ?step oe-agtorch:stepSatisfiesHardConstraint ?constraint .
  }
}
ORDER BY ?plan ?constraint ?requirement ?stepLabel

# ======================================================================================================================
# CQ 1. What orchestration plan should the agent follow to answer Ken's request for supplement recommendations,
#       given his preference for few tool calls and low token use?
# Reasoning: OWL 2 DL entailment (needs a DL reasoner). Run in Snap SPARQL with Pellet or HermiT started.
#   No plan is asserted to be selected. SelectedOrchestrationPlan is a defined class: a candidate orchestration plan
#   whose plan evaluation has rank 1. The reasoner classifies Ken plan 1 into it from its evaluation, so without a
#   reasoner this query returns no rows. Tools are listed for a step only when they provide the capability its task
#   requires.
# Individuals: kenRequest; kenPlan1 and its plan evaluation (rank 1); steps k1s1-k1s9 and their tasks; the skills,
#   tools and MCP servers behind the tasks.
# Expected answer: Ken plan 1 and its nine steps, with the tool calls of steps 2, 4 and 6 (10 rows):
#   planLabel | stepLabel | taskLabel | skillLabel | tool | toolServer
#   Ken plan 1 | Ken plan 1, step 1 | get user profile (Ken) |  |  | 
#   Ken plan 1 | Ken plan 1, step 2 | get candidate supplements (Ken) | personalized supplement recommendation skill | recommend_supplement | Supplement Advisor MCP server
#   Ken plan 1 | Ken plan 1, step 3 | remove redundant supplements (Ken) |  |  | 
#   Ken plan 1 | Ken plan 1, step 4 | get supplement products sorted by price (Ken) | product selection skill | search | 
#   Ken plan 1 | Ken plan 1, step 5 | rank supplement products by cost (Ken) |  |  | 
#   Ken plan 1 | Ken plan 1, step 6 | verify evidence (Ken) | evidence verification skill | download_articles_batch | PubMed MCP server
#   Ken plan 1 | Ken plan 1, step 6 | verify evidence (Ken) | evidence verification skill | search_articles | PubMed MCP server
#   Ken plan 1 | Ken plan 1, step 7 | rank supplement products by evidence (Ken) |  |  | 
#   Ken plan 1 | Ken plan 1, step 8 | select supplement product (Ken) | product selection skill |  | 
#   Ken plan 1 | Ken plan 1, step 9 | produce recommendation (Ken) |  |  | 
SELECT ?planLabel ?stepLabel ?taskLabel ?skillLabel ?tool ?toolServer
WHERE {
  ?plan a oe-agtorch:SelectedOrchestrationPlan .
  ?plan oe-agtorch:addresses oe-agtorch-ind:kenRequest .
  ?plan rdfs:label ?planLabel .
  ?plan oe-agtorch:hasStep ?step .
  ?step rdfs:label ?stepLabel .
  ?step agento:hasAssociatedTask ?task .
  ?task rdfs:label ?taskLabel .
  OPTIONAL {
    ?task oe-agtorch:performedBySkill ?skill .
    ?skill rdfs:label ?skillLabel .
    OPTIONAL {
      ?task agento:requiresCapability ?capability .
      ?skill oe-agtorch:usesTool ?toolInd .
      ?toolInd oe-agtorch:hasCapability ?capability .
      ?toolInd skos:altLabel ?tool .
      OPTIONAL {
        ?server oe-agtorch:exposes ?toolInd .
        ?server rdfs:label ?toolServer .
      }
    }
  }
}
ORDER BY ?stepLabel ?tool

# CQ 3. What skills are required to satisfy Jessica's request for supplement recommendations, given she explicitly
#       mentions her diagnosis and prescribed medication?
# Reasoning: none beyond the asserted triples (no RDFS or OWL inference). Run in the SPARQL Query tab; Snap SPARQL
#   gives the same rows.
#   A skill is kept when one of its capabilities satisfies an information requirement that Jessica's request
#   expresses, or a hard constraint derived from a preference setting of the person the request is attributed to.
# Individuals: jessicaRequest, Jessica, jessicaEvidenceSetting and jessicaSafetySetting, the three information
#   requirements and two hard constraints, the skills and their capabilities.
# Expected answer: the four skills of the use case answer (4 rows):
#   skillLabel | capabilityLabel | requirementLabel | hardConstraintLabel
#   evidence verification skill | evidence verification capability | supporting scientific evidence (Jessica) | evidence verification (Jessica)
#   personalized supplement recommendation skill | supplement recommendation capability | supplement recommendations (Jessica) | 
#   product selection skill | product search capability | purchasable supplement products (Jessica) | 
#   supplement safety screening skill | interaction screening capability |  | safety screening against celecoxib (Jessica)
SELECT ?skillLabel ?capabilityLabel ?requirementLabel ?hardConstraintLabel
WHERE {
  ?skill a oe-agtorch:Skill .
  ?skill rdfs:label ?skillLabel .
  ?skill oe-agtorch:hasCapability ?capability .
  ?capability rdfs:label ?capabilityLabel .
  OPTIONAL {
    oe-agtorch-ind:jessicaRequest oe-agtorch:expresses ?requirement .
    ?capability oe-agtorch:satisfiesRequirement ?requirement .
    ?requirement rdfs:label ?requirementLabel .
  }
  OPTIONAL {
    oe-agtorch-ind:jessicaRequest prov:wasAttributedTo ?person .
    ?settings a oe-agtorch:PreferenceSetting .
    ?settings prov:wasAttributedTo ?person .
    ?constraint a oe-agtorch:HardConstraint .
    ?constraint prov:wasDerivedFrom ?settings .
    ?constraint rdfs:label ?hardConstraintLabel .
    ?capability oe-agtorch:satisfiesConstraint ?constraint .
  }
  FILTER (BOUND(?requirementLabel) || BOUND(?hardConstraintLabel))
}
ORDER BY ?skillLabel

# CQ 5. Why was each agent capability chosen to execute in a given orchestration plan? (Dante's plan from the CQ 4 example)
# Reasoning: OWL 2 DL entailment (needs a DL reasoner). Run in Snap SPARQL with Pellet or HermiT started.
#   Dante's plan is selected by inference, as in CQ 1. For each step, the capability its task requires is listed
#   with the information requirement of Dante's request or the constraint from his preference settings that it
#   satisfies, and with the skill and MCP server that provide it.
# Individuals: danteRequest, Dante, danteSettings, dantePlan and its plan evaluation, steps d1-d5 and their tasks,
#   capabilities, skills, tools and servers.
# Expected answer: every capability in Dante's plan is justified by one of his requirements or constraints (5 rows):
#   stepLabel | taskLabel | skillLabel | toolServer | capabilityLabel | requirementLabel | constraintLabel
#   Dante's orchestration plan, step 1a | verify evidence (magnesium glycinate) | evidence verification skill | PubMed MCP server | evidence verification capability | evidence summary (Dante) | 
#   Dante's orchestration plan, step 1b | screen interactions (magnesium glycinate) | supplement safety screening skill | OpenFDA MCP server | interaction screening capability |  | safety screening (Dante)
#   Dante's orchestration plan, step 2a | verify evidence (magnesium citrate) | evidence verification skill | PubMed MCP server | evidence verification capability | evidence summary (Dante) | 
#   Dante's orchestration plan, step 2b | screen interactions (magnesium citrate) | supplement safety screening skill | OpenFDA MCP server | interaction screening capability |  | safety screening (Dante)
#   Dante's orchestration plan, step 3 | synthesize evidence (Dante) | evidence synthesis skill |  | evidence synthesis capability | comparison of magnesium glycinate and magnesium citrate (Dante) | 
SELECT DISTINCT ?stepLabel ?taskLabel ?skillLabel ?toolServer ?capabilityLabel ?requirementLabel ?constraintLabel
WHERE {
  ?plan a oe-agtorch:SelectedOrchestrationPlan .
  ?plan oe-agtorch:addresses oe-agtorch-ind:danteRequest .
  ?plan oe-agtorch:hasStep ?step .
  ?step rdfs:label ?stepLabel .
  ?step agento:hasAssociatedTask ?task .
  ?task rdfs:label ?taskLabel .
  ?task agento:requiresCapability ?capability .
  ?capability rdfs:label ?capabilityLabel .
  OPTIONAL {
    ?task oe-agtorch:performedBySkill ?skill .
    ?skill rdfs:label ?skillLabel .
  }
  OPTIONAL {
    ?task oe-agtorch:performedBySkill ?skill .
    ?skill oe-agtorch:usesTool ?toolInd .
    ?toolInd oe-agtorch:hasCapability ?capability .
    ?server oe-agtorch:exposes ?toolInd .
    ?server rdfs:label ?toolServer .
  }
  OPTIONAL {
    oe-agtorch-ind:danteRequest oe-agtorch:expresses ?requirement .
    ?capability oe-agtorch:satisfiesRequirement ?requirement .
    ?requirement rdfs:label ?requirementLabel .
  }
  OPTIONAL {
    oe-agtorch-ind:danteRequest prov:wasAttributedTo ?person .
    ?settings a oe-agtorch:PreferenceSetting .
    ?settings prov:wasAttributedTo ?person .
    ?constraint prov:wasDerivedFrom ?settings .
    ?capability oe-agtorch:satisfiesConstraint ?constraint .
    ?constraint rdfs:label ?constraintLabel .
  }
  FILTER (BOUND(?requirementLabel) || BOUND(?constraintLabel))
}
ORDER BY ?stepLabel

WHERE {
  ?eval oe-agtorch:evaluates ?plan .
  ?eval oe-agtorch:hasRank ?rank .
  FILTER (?rank = 1)
  ?plan oe-agtorch:addresses oe-agtorch-ind:danteRequest .
  ?plan oe-agtorch:hasStep ?step .
  ?step rdfs:label ?stepLabel .
  ?step agento:hasAssociatedTask ?task .
  ?task rdfs:label ?taskLabel .
  ?task agento:requiresCapability ?capability .
  ?capability rdfs:label ?capabilityLabel .
  OPTIONAL {
    ?task oe-agtorch:performedBySkill ?skill .
    ?skill rdfs:label ?skillLabel .
  }
  OPTIONAL {
    ?task oe-agtorch:performedBySkill ?skill .
    ?skill oe-agtorch:usesTool ?toolInd .
    ?toolInd oe-agtorch:hasCapability ?capability .
    ?server oe-agtorch:exposes ?toolInd .
    ?server rdfs:label ?toolServer .
  }
  OPTIONAL {
    oe-agtorch-ind:danteRequest oe-agtorch:expresses ?requirement .
    ?capability oe-agtorch:satisfiesRequirement ?requirement .
    ?requirement rdfs:label ?requirementLabel .
  }
  OPTIONAL {
    oe-agtorch-ind:danteRequest prov:wasAttributedTo ?person .
    ?settings a oe-agtorch:PreferenceSetting .
    ?settings prov:wasAttributedTo ?person .
    ?constraint prov:wasDerivedFrom ?settings .
    ?capability oe-agtorch:satisfiesConstraint ?constraint .
    ?constraint rdfs:label ?constraintLabel .
  }
  FILTER (BOUND(?requirementLabel) || BOUND(?constraintLabel))
}
ORDER BY ?stepLabel
